# DECISIONS: S-2000 Project Cost Control

บันทึกการตัดสินใจเรื่องที่สเปกไม่ได้ระบุ เรียงตามลำดับที่ตัดสินใจ

## โครงสร้างโปรเจกต์

1. แอปใหม่อยู่ที่ `cost-control/` ในรีโป s2000-hr แยก package.json, Supabase project และ Vercel project จากแอป HR เพราะ HR ใช้ NextAuth กับ LINE login และเขียน DB ผ่าน anon key โดยไม่มี RLS ถ้ารวม DB จะปนกันและเสี่ยงเปิดสิทธิ์ผิด ยืม convention โฟลเดอร์ migration (คอมเมนต์ไทย รันใน SQL Editor), date helper แบบ Asia/Bangkok และฟอนต์ Noto Sans Thai ผ่าน next/font มาใช้
2. Supabase client แยก 3 ตัว: browser (`src/lib/supabase/client.ts`), server ผ่าน cookie (`server.ts`) สำหรับ Server Component และ Server Action, service role (`admin.ts`) เฉพาะ notification, cron และ seed ห้าม import จาก client
3. ใช้ `src/proxy.ts` (ชื่อใหม่ของ middleware ใน Next.js 16) refresh session และบังคับ login ทุกหน้า ยกเว้น `/login` และ `/offline`
4. shadcn/ui เขียน component ลงรีโปโดยตรง (button, input, select, dialog, table, badge, card, alert) ไม่ใช้ CLI เพราะต้องควบคุมให้ไม่มีไอคอนและ touch target 44px `select` ใช้ native select เพื่อใช้บนมือถือได้ดี

## ฐานข้อมูล

5. ตารางเฟส 2 และ 3 ที่ผูก FK กับตารางเฟส 1 (subcontract_agreements, work_completion_certificates) สร้างไว้ตั้งแต่เฟส 1 พร้อม RLS เพื่อให้ view `v_boq_item_costs` นับ actual ของผู้รับเหมาช่วงได้โดยไม่ต้องแก้ view ทีหลัง ตารางที่เหลือ (tasks, progress_updates, closeouts, price_history, issues) สร้างในเฟสของตัวเอง
6. เลขเอกสาร `PR-YYMM-NNNN` และ `PO-YYMM-NNNN` ออกจากตาราง `document_counters` ต่อเดือน (เวลาไทย) ผ่านฟังก์ชัน `next_document_no`
7. การเปลี่ยนสถานะเอกสารสำคัญ (ยืนยัน BOQ, ส่ง PR, อนุมัติ/ปฏิเสธ, ออก PO, สร้าง VO) ทำผ่านฟังก์ชัน `security definer` ที่ตรวจสิทธิ์เอง ไม่เปิด update policy ให้แก้สถานะตรง เพื่อให้ routing และ approvals ถูกบันทึกครบทุกครั้ง
8. รายการ "นอก BOQ" (`is_off_boq = true`, item_no `OFF`) สร้างอัตโนมัติตอนยืนยัน version และถูก copy ไปทุก VO รายการนี้เป็นรายการเดียวใน version ที่ยืนยันแล้วซึ่ง trigger ยอมให้ insert
9. VO: `create_variation_order` copy หมวดและรายการทั้งหมดจาก version ที่ยืนยัน โดยเก็บ `origin_item_id` เมื่อยืนยัน VO ระบบย้าย `boq_item_id` ของ PR, PO, รับของ, expenses และสัญญาผู้รับเหมาช่วง จากรายการเดิมไปยังรายการใหม่ ทำให้ view คำนวณจาก version ปัจจุบันได้โดยไม่ต้อง resolve สายโซ่ version (audit log บันทึกการย้ายนี้)
10. `paid` ต่อรายการ BOQ: invoice ผูกระดับ PO ไม่ใช่ระดับรายการ จึงกระจายยอดชำระของ PO ลงรายการตามสัดส่วนมูลค่ารายการใน PO (`qty × unit_price / total PO`) expenses นับเป็น actual และ paid เต็มจำนวนทันที
11. `committed` = Σ (qty PO − qty รับแล้ว) × ราคา PO ของ PO ที่ไม่ยกเลิก เมื่อรับครบ committed เป็น 0 และ actual ใช้ราคาที่รับจริง (สต็อกภายในใช้ราคาทุน)
12. `forecast_profit` = contract_value − (actual + committed + (qty − qty สั่งแล้ว) × unit_cost) รายการที่รับเกิน BOQ ไม่ติดลบส่วนที่ยังไม่สั่ง (greatest 0)
13. สถานะสีบน card ในเฟส 1 ที่ยังไม่มีความก้าวหน้า: ต้นทุนเกินงบหรือกำไรพยากรณ์ติดลบ = เตือน, ต้นทุน > 95% ของงบ = เฝ้าระวัง เมื่อเฟส 2 มี progress_pct จะใช้กติกา ส่วนต่าง ≤ 0 / 0 ถึง 5 / > 5 ตามสเปกโดยอัตโนมัติ (โค้ดใน `project-card.tsx` เช็ค cost_vs_progress ก่อน)
14. View ใช้ `security_invoker = true` ให้ RLS ของตารางต้นทางมีผลกับ view ทุกตัว
15. Storage bucket `project-files` เป็น private path ขึ้นต้น `projects/<project_id>/` policy ตรวจ `can_view_project` จาก folder ที่ 2 อ่านผ่าน signed URL อายุ 1 ชั่วโมง
16. Audit trigger เขียนเฉพาะเมื่อค่าเปลี่ยนจริง (ไม่นับ updated_at) และเก็บ `auth.uid()` ของผู้ทำ; service role จะได้ user_id null

## สิทธิ์

17. purchasing และ accounting ดูได้ทุกโครงการ (ไม่ต้องเป็นสมาชิก) เพราะต้องออก PO และบันทึก invoice ข้ามโครงการ engineer / site_supervisor / project_manager เห็นเฉพาะโครงการที่เป็นสมาชิก
18. management อนุมัติ PR ได้ทั้งขั้น PM และขั้น management ถ้า management อนุมัติที่ขั้น PM ระบบข้ามขั้น management ทันที
19. PR ที่มีหลายรายการใช้กติกาจากรายการที่แย่ที่สุด: รายการใดเกิน BOQ (หรือเป็นนอก BOQ) หรือมูลค่ารวมเกิน `pm_approval_limit` จะต้องผ่าน management
20. ผู้สร้างโครงการ (management/admin/project_manager) เป็นสมาชิกโครงการอัตโนมัติ
21. profiles: ผู้ใช้แก้ชื่อและ line_user_id ของตัวเองได้ แต่ trigger ห้ามเปลี่ยน role, is_active, branch_id ยกเว้น admin

## จัดซื้อ

22. ฝ่ายจัดซื้อแก้ราคาตอนออก PO ได้ ถ้าราคาใหม่แพงกว่าราคาใน PR เกิน threshold ระบบจะไม่ออก PO แต่ปรับราคาใน PR ตั้ง flag ใหม่ และส่ง PR กลับเข้า routing ตั้งแต่ขั้น PM (PO status enum ไม่มีสถานะรออนุมัติ จึงคุมที่ PR แทน)
23. PR ที่ถูกปฏิเสธ เจ้าของแก้ไขและส่งใหม่ได้ (สถานะ rejected ถือเป็นร่างที่แก้ได้)
24. ยกเลิก PO ได้เฉพาะ PO ที่ยังไม่มีการรับของ
25. รับของ: site_supervisor และ project_manager ที่เป็นสมาชิกโครงการ รวมถึง purchasing และ management รับของได้ รับบางส่วนได้ สถานะ PO อัปเดตอัตโนมัติด้วย trigger
26. ใบแจ้งหนี้: สถานะเป็น paid อัตโนมัติเมื่อ Σ payments ≥ amount (trigger) และกลับเป็น approved ถ้าลบ payment
27. price_history (เฟส 3) จะเขียนตอนยืนยันรับของผ่าน trigger ที่จะเพิ่มในเฟส 3 ไม่ทำในเฟส 1 เพื่อไม่ให้มีตารางที่ไม่มีหน้าจอใช้

## Offline และ PWA

28. Service worker เขียนเอง (`public/sw.js`) ไม่ใช้ next-pwa: หน้า HTML ใช้ network-first ตกมา cache แล้วหน้า `/offline`, ไฟล์ static ใช้ stale-while-revalidate ไม่ลงทะเบียนใน development
29. Offline queue เก็บใน IndexedDB (`idb`) ต่อ kind ฟอร์ม PR สร้าง `client_ref` (uuid) ก่อนส่ง server action ตรวจ `client_ref` ซ้ำเพื่อกันสร้าง PR ซ้ำเมื่อ retry `OfflineSync` ใน layout ส่งคิวเมื่อ online และทุก 60 วินาที
30. ฟอร์ม PR ที่ส่งขณะออนไลน์แล้ว network ล้มกลางทาง จะถูกเก็บเข้าคิวเช่นกัน (ใช้ client_ref เดิม)

## การแจ้งเตือน

31. notifications เขียนผ่าน service role เท่านั้น (ไม่มี insert policy ให้ authenticated) กันผู้ใช้สร้างแจ้งเตือนถึงคนอื่น ผู้ใช้อ่านและ mark read ของตัวเองได้
32. LINE channel มีโครงพร้อมแล้วใน `src/lib/notifications/line.ts` ถ้าไม่มี `LINE_MESSAGING_TOKEN` จะ log แทน เหตุการณ์ครบ 5 อย่างตามสเปก invoice ครบกำหนดใน 3 วันใช้ Vercel cron `/api/cron/invoice-due` รายวัน (ป้องกันด้วย `CRON_SECRET`) และกันแจ้งซ้ำวันเดียวกัน
33. โครงการเข้าสถานะเตือน จะแจ้งเมื่อมี progress (เฟส 2) เพราะกติกาสีต้องใช้ความก้าวหน้า

## นำเข้า BOQ

34. หาแถวหัวตารางอัตโนมัติจาก 30 แถวแรก (แถวที่มีข้อความ ≥ 3 ช่องและมีคำว่า รายการ/ปริมาณ/หน่วย) ตรวจจับ mapping จากชื่อคอลัมน์ไทย/อังกฤษ ผู้ใช้แก้ได้ก่อนนำเข้า template บันทึกตามชื่อชีตแบบ upsert
35. แถวสรุป (รวม/ยอดรวม/total) ที่ไม่มีลำดับและไม่มีปริมาณถูกข้าม ไม่กลายเป็นหมวด
36. แถวที่มีแต่ยอดรวมต่อแถว (ไม่มีราคาวัสดุ/แรงงาน) ถือเป็น material โดย unit_cost = total / qty
37. ชีตที่ไม่มีหัวข้อหมวดเลย ใช้ชื่อชีตเป็นหมวด
38. markup: ถ้าไฟล์ไม่มีคอลัมน์ markup ใช้ค่าเริ่มต้นที่กรอกในหน้านำเข้า (ค่าเดียวทั้ง version) แก้รายรายการได้ตอน draft
39. VO นำเข้าผ่านหน้าเดียวกัน ไฟล์ไม่บังคับ ถ้ามีไฟล์ รายการในไฟล์จะถูกเพิ่มต่อท้ายรายการที่ copy มา

## ทดสอบ

40. Test ฐานข้อมูล (4 ชั้นตัวเลข, routing, RLS, VO, audit) รันกับ Postgres จริงผ่าน `TEST_DATABASE_URL` โดยใช้ shim `supabase/tests/00_supabase_shim.sql` เลียนแบบ schema auth/storage ของ Supabase ข้ามอัตโนมัติถ้าไม่ตั้ง env; test logic บริสุทธิ์ (routing, แตกแถว BOQ, variance decomposition, parse ไฟล์ตัวอย่าง) รันได้ทันที
41. Variance decomposition (เฟส 3) เขียนเป็นฟังก์ชันบริสุทธิ์และทดสอบตั้งแต่เฟส 1 ตามที่สเปกขอ test ครบ 5 หัวข้อ

## รูปแบบ BOQ จริงของ S-2000 (ปรับหลังได้ไฟล์ตัวอย่าง 5 ไฟล์)

42. ไฟล์ BOQ จริงใช้หัวตาราง 2 แถว แถวบนเป็นกลุ่ม (MATERIAL, LABOUR) แถวล่างเป็นหัวย่อย (@, SUB TOTAL) ตัวอ่านจึงรวมสองแถวเป็นชื่อเดียว เช่น "MATERIAL @" กับ "MATERIAL SUB TOTAL" ทำให้แยกราคาต่อหน่วยออกจากยอดรวมของหมวดเดียวกันได้
43. หาแถวหัวตารางด้วยการให้คะแนน แถวที่มีชื่อคอลัมน์ที่รู้จักมากที่สุดคือหัวตาราง แทนวิธีเดิมที่เลือกแถวแรกที่เจอคำใดคำหนึ่ง เพราะหัวกระดาษมีคำว่า PROJECT และ BILL OF QUANTITIES อยู่ด้านบน
44. จับคู่ชื่อคอลัมน์หลังตัดเครื่องหมายวรรคตอนออก ทำให้ `Q'TY` จับเป็นปริมาณได้ และ `ITEMS` จับเป็นลำดับได้ เดิมทั้งสองคอลัมน์จับไม่ได้ ทำให้ทุกแถวกลายเป็นหมวดและไม่ได้รายการเลย
45. ชีต BOQ จริงมีบล็อก SUMMARY สรุปยอดต่อหมวดอยู่เหนือรายละเอียด ตัวอ่านข้ามตั้งแต่แถวที่มีคำว่า SUMMARY จนถึงแถว Total ถ้าไม่ข้าม ต้นทุนจะถูกนับซ้ำสองเท่า
46. แถวสรุปที่ merge ทั้งแถว (Sub Total, Total, Overhead & Profit) จะมีข้อความเดียวกันทั้งในคอลัมน์ลำดับและคอลัมน์รายการ ใช้เงื่อนไขนี้ระบุว่าไม่มีลำดับ แล้วข้ามด้วยรูปแบบคำขึ้นต้น
47. `\b` ใช้กับข้อความไทยไม่ได้เพราะอักษรไทยไม่ใช่ word character ของ JavaScript regex จึงตัดออกจากรูปแบบที่ใช้จับแถวสรุป
48. ช่องราคาที่เขียนว่า By Owner แปลว่าผู้ว่าจ้างจัดหาให้ ต้นทุนของเราเป็นศูนย์ ตัวอ่านเก็บรายการไว้ที่ราคา 0 ไม่ทิ้งบรรทัด
49. หมวดสร้างจริงเมื่อเจอรายการแรกใต้หัวข้อเท่านั้น หัวข้อที่ไม่มีรายการ (SUMMARY, หมายเหตุ, หมวดที่มีแต่หมวดย่อย) จึงไม่กลายเป็นหมวดค้างในระบบ ชื่อหมวดใช้หัวข้อย่อยสุด และเก็บหัวข้อที่ครอบอยู่ไว้ในคอลัมน์ code (เปลี่ยนความหมายจากเดิมที่เก็บเลขลำดับของหัวข้อ)
50. ชีตที่ไม่มีคอลัมน์ราคาวัสดุหรือค่าแรงจะไม่ถูกติ๊กนำเข้าอัตโนมัติ เพราะเป็นชีตปกหรือใบเสนอราคาที่มีแต่ยอดรวม ถ้านำเข้าพร้อมชีต BOQ จะนับต้นทุนซ้ำ
51. ไฟล์ VO ที่มีหมวดงานลด (เช่น "หมวดงานสถาปัตย์ (ตามสัญญาเดิม) งานลด") เก็บตัวเลขเป็นบวกในไฟล์ แล้วหักลบกันที่บล็อกสรุป ผู้ใช้ตัดสินใจให้นำเข้าเป็นรายการติดลบ รายละเอียดตามข้อ 75 ถึง 79
52. ตรวจผลกับไฟล์จริง 5 ไฟล์ ทุกชีตรายละเอียดให้ต้นทุนรวมตรงกับ Sub Total ในไฟล์ทุกบาท ยกเว้นไฟล์ VO ที่ต่างเพราะการหักลบตามข้อ 51 ไฟล์จริงไม่ถูก commit ลงรีโป ใช้ fixture สังเคราะห์ที่จำลองโครงสร้างเดียวกันใน tests/unit/boq-s2000-format.test.ts แทน

53. คอลัมน์ markup ต้องเป็นเปอร์เซ็นต์กำไรจริงเท่านั้น เดิมจับด้วยเครื่องหมาย % อย่างเดียว ทำให้คอลัมน์ "ราคา+5%" ในใบเสนอราคาถูกจับเป็น markup แล้วกลายเป็น 6182.24% กำไรคาดหวังของโครงการเพี้ยนเป็น 98 เปอร์เซ็นต์ ตอนนี้ตัดคอลัมน์ที่มีคำว่า ราคา price บาท รวม หรือ จำนวน ออกจากการจับ markup
54. ถึงจับคอลัมน์ markup ได้ ก็ตรวจค่าทั้งคอลัมน์ก่อนใช้ ถ้ามีค่าใดออกนอกช่วง -100 ถึง 200 เปอร์เซ็นต์ ถือว่าจับผิดคอลัมน์ ทิ้งทั้งคอลัมน์แล้วใช้ค่า markup เริ่มต้นที่ผู้ใช้กรอกแทน พร้อมเตือนในหน้านำเข้า เลือกตรวจระดับคอลัมน์ไม่ใช่รายแถว เพื่อไม่ให้บางรายการใช้ค่าจากไฟล์และบางรายการใช้ค่าเริ่มต้นปนกัน
55. บรรทัดที่เป็นวันที่ล้วน เช่น 6-10-69 ไม่ถือเป็นหัวข้อหมวด เพราะในใบเสนอราคามักมีวันที่แทรกอยู่ในตาราง

56. ย้ายการตีความโครงไฟล์ไปให้ Claude อ่าน เพราะกฎจับคู่ชื่อคอลัมน์พังทันทีที่ผู้ประมาณราคาสะกดหัวคอลัมน์ต่างออกไปหรือพิมพ์ผิด และที่ผ่านมาพังจริงสองรอบ รอบแรก Q'TY จับไม่ได้เพราะมี apostrophe ทำให้ได้ 0 รายการทั้งไฟล์ รอบสอง ราคา+5% ถูกจับเป็น markup เพราะมีเครื่องหมายเปอร์เซ็นต์ในชื่อ ทำให้กำไรคาดหวังเพี้ยนเป็น 98 เปอร์เซ็นต์
57. ขอบเขตของ Claude จำกัดไว้ที่ metadata เท่านั้น คือคอลัมน์ไหนคืออะไร หัวตารางอยู่แถวไหน กี่แถว ข้อมูลจริงเริ่มแถวไหน และชีตนี้เป็น BOQ รายละเอียดหรือใบเสนอราคาสรุป ตัวเลขทุกตัวยังคำนวณด้วยโค้ดใน splitRows เหมือนเดิม ไฟล์เดียวกันกับการจับคู่เดียวกันจึงให้ผลเดิมทุกครั้งและตรวจย้อนหลังได้ ซึ่งเป็นคุณสมบัติที่ยอมเสียไม่ได้เพราะตัวเลขเหล่านี้คือเงิน
58. ใช้ structured outputs ผ่าน client.messages.parse กับ zod schema ทำให้ผลลัพธ์ผ่านการตรวจ schema เสมอ ไม่ต้อง parse ข้อความเอง
59. ลำดับการตัดสินใจคือ template ที่เคยบันทึก มาก่อน Claude มาก่อนกฎตายตัว เมื่อผู้ใช้กดนำเข้าสำเร็จ ระบบบันทึกทั้งการจับคู่คอลัมน์และโครงของชีตเป็น template ตามชื่อชีต ไฟล์หน้าตาเดิมครั้งถัดไปจึงไม่เรียก Claude อีก ค่าใช้จ่ายจึงเกิดครั้งเดียวต่อรูปแบบไฟล์

## สิทธิ์แก้ไขและลบของฝ่ายบริหาร

64. เพิ่มการลบโครงการ การยกเลิกการยืนยัน BOQ และการลบ BOQ ทั้งเวอร์ชัน ให้ฝ่ายบริหารและผู้ดูแลระบบ เพราะตอนทดสอบและตอนใช้งานจริงย่อมมีการยืนยันผิดไฟล์หรือสร้างโครงการทดลองทิ้งไว้ ถ้าแก้ไม่ได้เลยระบบจะใช้งานจริงไม่ได้
65. เงื่อนไขเดียวที่ยังล็อกคือ โครงการต้องไม่มีเอกสารต้นทุน ได้แก่ใบขอซื้อ ใบสั่งซื้อ ใบแจ้งหนี้ ค่าใช้จ่าย และสัญญาผู้รับเหมาช่วง เพราะถ้าแก้งบทับหลังสั่งซื้อไปแล้ว ระบบจะอธิบายไม่ได้ว่ากำไรจริงต่างจากที่คาดเพราะอะไร ซึ่งเป็นเหตุผลหลักที่สร้างระบบนี้ขึ้นมา ในกรณีนั้นต้องแก้ด้วยการทำ VO ตามเดิม
66. ป้องกันสามชั้น ชั้นแรก RLS เปิดสิทธิ์ลบเฉพาะ management กับ admin ชั้นสอง ฟังก์ชันและ server action ตรวจเอกสารต้นทุนก่อนแล้วตอบเหตุผลเป็นภาษาไทยพร้อมจำนวนเอกสารที่ขวางอยู่ ชั้นสาม foreign key ของตารางเอกสารต้นทุนตั้งไว้แบบไม่ cascade โดยตั้งใจ ฐานข้อมูลจึงปฏิเสธเองแม้โค้ดสองชั้นแรกพลาด
67. การยกเลิกการยืนยันไม่ได้ปลด trigger ที่ห้ามย้อนสถานะ แต่ใช้ค่า setting ระดับ transaction เป็นตัวปลดเฉพาะตอนที่คำสั่งมาจากฟังก์ชัน unconfirm_boq_version จึงปลอมจากฝั่งแอปไม่ได้
68. การลบโครงการบังคับให้พิมพ์รหัสโครงการยืนยัน เพราะย้อนกลับไม่ได้และลบ BOQ ทุกเวอร์ชันไปด้วย
69. เมื่อยกเลิกการยืนยันแล้วโครงการไม่เหลือ BOQ ที่ยืนยัน โครงการจะกลับไปเป็นร่างและหายจากแดชบอร์ดจนกว่าจะยืนยันใหม่ เวอร์ชันที่เคยถูกแทนที่ไม่ถูกดึงกลับมาอัตโนมัติ เพราะระบบไม่ได้เก็บว่าเวอร์ชันไหนแทนที่เวอร์ชันไหน ข้อนี้เขียนบอกไว้ในกล่องยืนยันแล้ว
70. การลบโครงการถูกบันทึกใน audit log พร้อมค่าเดิมทั้งแถว ผ่าน trigger เดิมที่ครอบ DELETE อยู่แล้ว

## แก้ BOQ ที่ยืนยันแล้วโดยไม่ต้องอัปโหลดไฟล์

71. เพิ่มปุ่มแก้ไข BOQ ในหน้าโครงการ กดแล้วระบบเปิดร่างให้ทันที แก้ปริมาณของรายการเดิมหรือกดเพิ่มรายการใหม่ได้ แล้วกดยืนยันครั้งเดียว ไม่ต้องอัปโหลดไฟล์ใหม่ ความสามารถนี้มีอยู่แล้วผ่านการสร้าง VO แต่ปุ่มอยู่ลึกในหน้า BOQ เวอร์ชัน คนหาไม่เจอ
72. เบื้องหลังยังเป็น VO เหมือนเดิม ไม่ได้แก้ทับเวอร์ชันที่ยืนยันแล้ว เวอร์ชันเดิมถูกเก็บเป็นประวัติ และตอนยืนยัน ต้นทุนที่เกิดไปแล้วย้ายมาผูกกับรายการในเวอร์ชันใหม่ผ่าน origin_item_id ตามกลไกเดิม ข้อนี้ทำให้แก้ปริมาณได้แม้โครงการจะมีใบสั่งซื้อและการรับของไปแล้ว ต่างจากการยกเลิกการยืนยันที่ทำได้เฉพาะตอนยังไม่มีเอกสารต้นทุน
73. create_variation_order เปลี่ยนให้ใช้ร่าง VO เดิมถ้ามีค้างอยู่ แทนการสร้างเวอร์ชันใหม่ทุกครั้งที่กด เดิมกดสองครั้งจะได้ร่างค้างสองอัน
74. ร่างที่ยังไม่ยืนยันขึ้นคำอธิบายในหน้า BOQ เวอร์ชันว่าเวอร์ชันที่ใช้งานอยู่ยังไม่เปลี่ยนจนกว่าจะกดยืนยัน

## งานลดใน VO (ผู้ใช้ตัดสินใจ: นำเข้าเป็นบรรทัดติดลบ)

75. รายการใต้หัวข้องานลดถูกนำเข้าเป็นปริมาณติดลบ ราคาต่อหน่วยเป็นบวกเสมอ ถ้าไฟล์เขียนเครื่องหมายลบไว้เองที่ช่องปริมาณหรือช่องราคา ระบบใช้ค่าสัมบูรณ์ก่อนแล้วจึงใส่เครื่องหมายลบที่ปริมาณ ยอดจึงหักออกเสมอและไม่กลับเป็นบวกซ้ำ เลือกเครื่องหมายที่ปริมาณเพราะหน้าจอแสดง "−20 ตร.ม" ซึ่งอ่านออกทันทีว่าเป็นงานที่ลด
76. หัวข้องานลดจับด้วยคำ งานลด ลดงาน (ลด) รายการลด deduct omit โดยคำว่า งานลด ต้องจบคำ เพื่อไม่ให้ไปจับงานจริงอย่าง งานลดระดับพื้น หมวดย่อยที่อยู่ใต้หัวข้องานลดเป็นงานลดทั้งหมดจนกว่าจะเจอหมวดใหญ่ใหม่ ตัดสินด้วยโค้ด ไม่ให้ Claude ตัดสิน เพราะเป็นการเปลี่ยนเครื่องหมายของเงิน หน้านำเข้าแสดงชื่อหัวข้อและจำนวนรายการที่ถูกกลับเครื่องหมาย ถ้าจับผิด แก้ปริมาณเป็นบวกในร่างก่อนยืนยันได้
77. รายการติดลบผูกต้นทุนไม่ได้ ทั้งใบขอซื้อ ใบสั่งซื้อ รับของ ค่าใช้จ่าย และสัญญาผู้รับเหมาช่วง บังคับด้วย trigger `guard_deduction_item` ที่ฐานข้อมูล และซ่อนรายการเหล่านี้จากตัวเลือกในหน้าขอซื้อและหน้าบันทึกค่าใช้จ่าย ถ้าซื้อของให้งานที่ถูกลดไปแล้ว ต้องลงที่รายการเดิมหรือรายการนอก BOQ ซึ่งจะเห็นชัดว่าเกินงบสุทธิ
78. ต้นทุนคาดการณ์ของโครงการ (`v_project_summary.forecast_profit`) หักงานลดออกเต็มจำนวน เดิมส่วนที่ยังไม่สั่งคิดเป็น max(ปริมาณ − ที่สั่งแล้ว, 0) ซึ่งทำให้รายการติดลบมีค่าเป็นศูนย์และงานลดไม่มีผลกับคาดการณ์ (migration 20261016_0008)
79. มูลค่าสัญญาไม่ถูกปรับอัตโนมัติตาม VO ผู้ใช้แก้เองที่หน้าแก้ไขโครงการ เพราะยอดที่ลูกค้าตกลงจริงอาจต่างจากราคาขายใน BOQ (ต่อรองราคา ปัดเศษ)

## VAT

80. ราคาทุกตัวในระบบเก็บเป็นราคาไม่รวม VAT ได้แก่ต้นทุนใน BOQ ราคาในใบขอซื้อและใบสั่งซื้อ ราคาทุนตอนรับของ ค่าใช้จ่าย ใบแจ้งหนี้ การจ่ายเงิน และมูลค่าสัญญา เพราะ VAT ซื้อขอคืนได้ ไม่ใช่ต้นทุนของโครงการ และทำให้งบ ยอดผูกพัน ยอดจริง และยอดจ่าย เทียบกันได้ตรงกันทุกชั้น ทุกช่องที่กรอกราคามีวงเล็บบอกว่าไม่รวม VAT
81. ใบขอซื้อ และการแก้ราคาตอนออกใบสั่งซื้อ (ซึ่งส่งกลับไปอนุมัติใหม่ได้) มีราคาสองช่อง ไม่รวม VAT และรวม VAT กรอกช่องไหนอีกช่องคำนวณให้ ช่องที่กรอกล่าสุดเป็นตัวตั้ง ช่องรวม VAT เป็นตัวช่วยกรอกจากใบเสนอราคาของซัพพลายเออร์ที่มักเขียนยอดรวม VAT ระบบบันทึกเฉพาะราคาไม่รวม VAT ปัดทศนิยม 2 ตำแหน่ง หน้ารายละเอียดใบขอซื้อและใบสั่งซื้อแสดงมูลค่ารวมทั้งสองแบบ
82. อัตรา VAT 7% เป็นค่าคงที่ใน `src/lib/vat.ts` ยังไม่ทำเป็นค่าตั้งในฐานข้อมูล ถ้าอัตราเปลี่ยนแก้ที่จุดเดียว ราคาที่บันทึกไว้แล้วไม่กระทบเพราะเก็บแบบไม่รวม VAT

## ซัพพลายเออร์

83. ชื่อซัพพลายเออร์ที่พิมพ์ในใบขอซื้อ ใบสั่งซื้อ หรือใบแจ้งหนี้ ถูกบันทึกเข้ารายชื่อซัพพลายเออร์อัตโนมัติผ่านฟังก์ชัน `ensure_supplier` (security definer) เดิมชื่อที่พิมพ์ในใบขอซื้อเก็บเป็นข้อความในรายการนั้นอย่างเดียว ไม่เข้ารายชื่อ จึงไม่ขึ้นให้เลือกตอนออกใบสั่งซื้อ
84. ใบขอซื้อผูกชื่อกับรายชื่อด้วย trigger ที่ฐานข้อมูล ครอบทุกทางที่สร้างใบขอซื้อรวมถึงคิวออฟไลน์ ชื่อที่เคยพิมพ์ไว้ในใบขอซื้อเดิมถูกย้อนเก็บเข้ารายชื่อตอนรัน migration 20261017_0009
85. ชื่อที่ต่างกันแค่ตัวพิมพ์เล็กใหญ่หรือช่องว่างถือเป็นรายเดียวกัน ไม่ได้รวมชื่อที่เขียนต่างแบบ เช่น บจก. กับ บริษัท ... จำกัด เพราะเสี่ยงรวมบริษัทที่ต่างกันจริง ช่องค้นหาที่กรองตามตัวอักษรช่วยให้เลือกชื่อเดิมแทนการพิมพ์ใหม่
86. ผู้ขอซื้อทุกบทบาทเพิ่มชื่อซัพพลายเออร์ได้ผ่านการพิมพ์ในเอกสาร แต่แก้หรือลบรายชื่อได้เฉพาะจัดซื้อ ฝ่ายบริหาร และผู้ดูแลระบบ ตาม RLS เดิม การสร้างทุกครั้งอยู่ใน audit log

## โหมดบันทึกซื้อตรง (ช่วงใช้งานคนเดียว)

87. ผู้ใช้ขอตัดขั้นตอนออกใบสั่งซื้อและรับของออกชั่วคราว เพราะช่วงนี้ใช้คนเดียวเพื่อติดตามต้นทุนแบบ realtime เลือกทำเป็นโหมดในตาราง settings (`direct_purchase_mode`) แทนการลบขั้นตอน การบันทึกการสั่งซื้อหนึ่งครั้งยังสร้างใบขอซื้อ การอนุมัติ ใบสั่งซื้อ และการรับของครบทุกชั้นผ่านฟังก์ชัน `record_direct_purchase` ตัวเลข 4 ชั้นและ view เดิมจึงไม่ต้องแก้ และเมื่อปิดโหมดภายหลัง ระบบกลับไปใช้ขั้นตอนเต็มได้โดยไม่ต้องย้ายข้อมูล
88. รับของเต็มจำนวนอัตโนมัติ ต้นทุนจึงเข้าเป็นต้นทุนจริงทันที ถ้าเก็บเป็นใบสั่งซื้อค้างรับ ตัวเลขจะไปอยู่ที่ยอดผูกพัน และรายการจะค้างในคิวรับของตอนเปิดขั้นตอนเต็มภายหลัง
89. การตรวจยังทำเหมือนเดิมทุกข้อ ทั้งเกินปริมาณ BOQ เกินราคาที่ทดไว้ และนอก BOQ ซึ่งต้องระบุเหตุผล เพราะเป็นจุดประสงค์ของการบันทึก การอนุมัติถูกบันทึกเป็นขั้น `direct` ใน approvals ให้ย้อนดูได้ว่ารายการไหนไม่ได้ผ่านการอนุมัติจริง
90. โหมดนี้ใช้ได้เฉพาะฝ่ายบริหารและผู้ดูแลระบบ บังคับที่ฐานข้อมูล บทบาทอื่นที่บันทึกระหว่างเปิดโหมดยังเข้าขั้นตอนขออนุมัติตามปกติ
91. เมนูใบสั่งซื้อและรับของแสดงเป็นสีเทา กดไม่ได้ พร้อมคำว่าปิดชั่วคราว ไม่ซ่อน เพื่อให้รู้ว่ามีขั้นตอนนี้อยู่และจะเปิดใช้ภายหลัง แถบล่างบนมือถือเปลี่ยนเป็น ภาพรวม บันทึกซื้อ รายการซื้อ โครงการ
92. บันทึกผิดแก้ด้วยการยกเลิกแล้วบันทึกใหม่ ผ่าน `void_direct_purchase` ซึ่งต้องมีเหตุผล ลบการรับของอัตโนมัติ และยกเลิกใบสั่งซื้อกับใบขอซื้อ ทุกแถวที่ลบอยู่ใน audit log ยกเลิกไม่ได้ถ้ามีใบแจ้งหนี้แล้ว จำเป็นต้องมี เพราะการรับของอัตโนมัติทำให้ปุ่มยกเลิกใบสั่งซื้อเดิมใช้ไม่ได้
97. ใบขอซื้อที่อนุมัติแล้วแต่ยังไม่ออกใบสั่งซื้อ (ค้างจากก่อนเปิดโหมด) ใช้ `record_direct_purchase` ได้เช่นกัน หน้าใบขอซื้อมีปุ่มบันทึกเป็นต้นทุนของโครงการ ไม่งั้นใบเหล่านี้จะค้างโดยไม่มีทางนับเป็นต้นทุน เพราะเมนูใบสั่งซื้อปิดอยู่

## ภาพรวมต้นทุน

93. หน้าแรกเปลี่ยนเป็นภาพรวมต้นทุน ตัวเลขใหญ่คือต้นทุนที่ใช้ไปรวมทุกโครงการเป็น % ของงบ ตามด้วยมูลค่าสัญญา งบต้นทุน ใช้ไปแล้ว กำไรคาดหวัง กำไรพยากรณ์ แล้วรายโครงการเรียงจากใช้ไปมากสุดเทียบงบ จอใหญ่เป็นตาราง มือถือเป็นการ์ด
94. ใช้ไปแล้ว = ต้นทุนจริง + ยอดผูกพัน เพราะยอดผูกพันคือเงินที่สัญญาจะจ่ายแล้ว นับรวมเพื่อเตือนก่อนเกินงบ ในโหมดบันทึกซื้อตรงยอดผูกพันเป็นศูนย์ สถานะสีของการ์ดในหน้าโครงการเปลี่ยนมาใช้ตัวเลขเดียวกัน
95. ยอดรวมนับเฉพาะโครงการที่ยืนยัน BOQ แล้ว โครงการที่ยังไม่มีงบมีกำไรพยากรณ์เท่ากับมูลค่าสัญญาเต็ม ถ้านับรวมจะทำให้กำไรพยากรณ์รวมสูงเกินจริง
96. แถบต้นทุนใช้สีสถานะเขียว ส้ม แดง ซึ่งผ่าน contrast แต่คู่เขียวกับส้มแยกยากสำหรับคนตาบอดสีบางแบบ จึงมีคำกำกับ ปกติ เฝ้าระวัง เตือน และเกินงบ ทุกแถบ ไม่ให้สีเป็นสิ่งเดียวที่บอกสถานะ

## Template การนำเข้า BOQ

98. template ที่บันทึกตามชื่อชีตเคยถูกใช้ก่อนเสมอและข้ามการอ่านด้วย Claude ไฟล์ของ S-2000 ส่วนใหญ่ใช้ชื่อชีตว่า BOQ เหมือนกัน แต่หัวตารางอยู่คนละแถวและคอลัมน์ต่างกัน template จากไฟล์ก่อนจึงทำให้ไฟล์ใหม่แตกได้ 0 รายการ (ไฟล์ V098 งานรางน้ำยางสแตนเลส)
99. ตอนนี้ Claude อ่านโครงทุกชีตเสมอ template ใช้ได้ต่อเมื่อหัวคอลัมน์ทุกคอลัมน์ที่จับคู่ไว้ตรงกับไฟล์เดิม (เก็บชื่อหัวคอลัมน์ไว้ใน template ตั้งแต่นี้) และแตกรายการได้ template รุ่นเก่าที่ไม่มีชื่อหัวคอลัมน์ ใช้ได้เฉพาะเมื่อตำแหน่งคอลัมน์รายการ ปริมาณ และราคา ตรงกับที่อ่านได้ใหม่ ถ้าไม่ตรงหน้านำเข้าบอกว่าไม่ได้ใช้รูปแบบเดิม
100. ลำดับที่เลือก template ที่ตรง แล้ว Claude แล้วกฎตายตัว แหล่งไหนแตกได้ 0 รายการลองแหล่งถัดไป ยกเว้นเมื่อ Claude ระบุว่าชีตนั้นไม่ใช่รายละเอียด BOQ (ปก ใบเสนอราคา) ซึ่งเชื่อ Claude ตรวจกับไฟล์ V098 ได้ 23 รายการ ต้นทุนรวม 3,916,660.00 บาท ตรงกับ Sub Total ในไฟล์

## มูลค่าสัญญาจากไฟล์ และการตรวจตัวเลขในไฟล์

101. หน้าสร้างโครงการไม่มีช่องมูลค่าสัญญาแล้ว ระบบอ่านจากไฟล์ BOQ ตอนนำเข้า หน้านำเข้าแสดงยอดที่อ่านได้ บอกว่ามาจากชีตและแถวไหน ให้แก้ตัวเลขได้ และมีช่องติ๊กว่าจะตั้งเป็นมูลค่าสัญญาหรือไม่ BOQ ใหม่ตั้งค่า VO บวกเพิ่ม (ค่าเริ่มต้นของ VO คือไม่ติ๊ก เพราะยอดที่ตกลงกับลูกค้าจริงอาจต่างจากไฟล์) แก้ภายหลังได้ที่หน้าแก้ไขโครงการ
102. มูลค่าสัญญาคือยอดก่อน VAT หลังหักส่วนลด เลือกจากใบเสนอราคาก่อน เพราะเป็นยอดที่ลูกค้าเห็นจริง (ไฟล์ V098: รวม 4,229,992.80 ส่วนลด 29,992.80 รวมทั้งสิ้น 4,200,000.00 แล้วจึง VAT) ถ้าไม่มีใบเสนอราคา ใช้ยอดสุดท้ายของชีตรายละเอียดหลังค่าดำเนินการ รวมทุกชีตที่นำเข้า
103. Claude ชี้เซลล์ที่เป็นมูลค่าสัญญาและบอกว่ารวม VAT หรือไม่ ตัวเลขอ่านจากเซลล์ในไฟล์เสมอ Claude ไม่พิมพ์ตัวเลขเอง ถ้า Claude ไม่ทำงาน ใช้กฎจากข้อความในแถว (รวม ส่วนลด VAT Total Overhead)
104. การตรวจตัวเลขในไฟล์ทำด้วยโค้ดทั้งหมด ไม่ให้ Claude คำนวณ เพราะจุดประสงค์คือกันตัวเลขผิด การคำนวณด้วยโมเดลภาษาผิดได้และตรวจซ้ำไม่ได้ Claude ช่วยแค่บอกว่าแถวไหนเป็นยอดรวมแบบไหน ตรวจ ปริมาณ × ราคาวัสดุ, ปริมาณ × ค่าแรง, วัสดุ + ค่าแรง = ราคาต่อหน่วยรวม, ยอดบรรทัด, ยอดหมวด, ยอดหมวดใหญ่, Sub Total, ค่าดำเนินการตามเปอร์เซ็นต์, Total หลังบวกลบ, VAT 7% ยอมให้ต่าง 1 บาทบวกเศษปัดของยอดใหญ่
105. ถ้าพบตัวเลขไม่ตรง ต้องติ๊กรับทราบก่อนนำเข้า งบต้นทุนในระบบคำนวณจาก ปริมาณ × ราคาต่อหน่วย อยู่แล้ว ยอดรวมที่ผิดในไฟล์จึงไม่เข้าไปในงบ แต่ใบเสนอราคาที่ส่งลูกค้าอาจผิด และราคาต่อหน่วยที่พิมพ์ผิดจะเข้าไปในงบ จึงต้องให้ผู้ใช้เห็นก่อน
106. หน้านำเข้าแยกสาเหตุที่ไม่ได้ใช้ Claude ให้ชัด: ไม่พบ ANTHROPIC_API_KEY บนเซิร์ฟเวอร์, เรียกแล้วไม่สำเร็จพร้อมสาเหตุ (key ผิด ไม่มีสิทธิ์ เครดิตหมด เชื่อมต่อไม่ได้), หรือ Claude อ่านแล้วแตกรายการไม่ได้ เดิมขึ้นข้อความว่ายังไม่ได้ตั้งค่าทุกกรณี
107. แก้ข้อมูลที่ส่งให้ Claude อ่าน: เดิมเซลล์ที่เป็นสูตร Excel ถูกส่งไปเป็น [object Object] ตัวเลขที่มาจากสูตรเกือบทั้งหมดใน BOQ จึงไม่ถึง Claude ตอนนี้ส่งผลลัพธ์ของสูตร และส่งแถวยอดรวมท้ายชีตไปด้วยแม้เกิน 45 แถวแรก
108. การเรียก Claude เปิด fallbacks: "default" ถ้าตัวกรองความปลอดภัยปฏิเสธ API ส่งต่อไปโมเดลสำรองเอง และเช็ค stop_reason ก่อนอ่านผล

## ต้นทุนจากคอลัมน์ต้นทุนของผู้ประมาณราคา (ผู้ใช้ยืนยัน)

109. BOQ ส่วนใหญ่ของ S-2000 ราคาวัสดุและค่าแรงในตารางหลักเป็นราคาขาย ต้นทุนจริงที่ผู้ประมาณราคาทดไว้ (ไม่รวม VAT) อยู่ในคอลัมน์ด้านขวา เช่น ต้นทุนวัสดุ /หน่วย ต้นทุนค่าแรง/หน่วย ผู้ใช้ยืนยันให้ใช้ต้นทุนนี้เป็นงบ และต้องเตือนเมื่อสั่งซื้อแพงกว่าต้นทุนนี้ ไฟล์ V098: เดิมงบ 3,916,660.00 (ราคาขาย) ตอนนี้ 3,290,172.04 เทียบกับในไฟล์ 3,290,175.89 ต่างกัน 3.85 บาทจากการเก็บต้นทุนต่อหน่วยสองตำแหน่ง (2,794.392523 เป็น 2,794.39)
110. หัวคอลัมน์ต้นทุนอยู่ในแถวหัวหมวด ไม่ใช่แถวหัวตารางหลัก จึงสแกนทั้งชีตหาคอลัมน์ที่เจอบ่อยที่สุด และเติมให้ทุกแหล่ง (template, Claude, กฎ) ที่ยังไม่ได้ระบุ ผู้ใช้ปิดได้โดยเลือก ไม่มี ในหน้านำเข้า
111. เมื่อมีคอลัมน์ต้นทุน: unit_cost = ต้นทุนต่อหน่วย, sell_unit_price = ราคาในตาราง BOQ, markup_pct = ราคาขายเทียบต้นทุน (เก็บไว้ดู) บรรทัดที่มีราคาขายแต่ไม่มีต้นทุน ใช้ราคาขายเป็นต้นทุน เพื่อไม่ให้งบต่ำกว่าจริงจนกำไรดูดีเกินจริง และนับแจ้งในหน้านำเข้า
112. ตรวจคอลัมน์ต้นทุนด้วย: ปริมาณ × ต้นทุนต่อหน่วย = ต้นทุนรวมของบรรทัด และแถวยอดรวมที่มีตัวเลขในคอลัมน์ต้นทุนรวมต้องเท่าผลรวมรายการ
113. หน้าบันทึกการสั่งซื้อเตือนทุกครั้งที่ราคาแพงกว่าต้นทุนที่ทดไว้ แม้ไม่ถึงเกณฑ์ 5% ที่บังคับเหตุผล บอกส่วนต่างต่อหน่วยและรวม
114. API key ระดับองค์กรที่ไม่ได้ผูกกับ workspace ต้องส่ง header anthropic-workspace-id รองรับผ่าน ANTHROPIC_WORKSPACE_ID (ไม่บังคับ)

## แก้ BOQ ที่ยืนยันแล้วได้ตลอด (ผู้ใช้ยืนยันซ้ำ แทนที่ข้อ 65 และหลักข้อ 3 เรื่องงบล็อก)

115. ผู้ใช้ขอสิทธิ์แก้ทั้งหมดสองครั้ง ครั้งแรกผมยังคงล็อกงบไว้หลังมีเอกสารต้นทุน ครั้งที่สองยืนยันว่าต้องแก้ได้ตลอด จึงทำตาม ฝ่ายบริหารและผู้ดูแลระบบแก้ปริมาณ ราคา เพิ่มและลบรายการในเวอร์ชันที่ยืนยันแล้วได้ตรงๆ แม้มีใบขอซื้อหรือรับของแล้ว ไม่ต้องเปิดร่างหรือทำ VO (migration 20261017_0011)
116. สิ่งที่ยังคงไว้เพื่ออธิบายกำไรที่เปลี่ยนไปได้: ทุกการแก้ไขถูกบันทึกใน audit log พร้อมค่าเดิม ค่าใหม่ ผู้แก้ และเวลา เวอร์ชันที่ถูกแทนที่แล้วยังล็อกเป็นประวัติ ผู้จัดการโครงการและวิศวกรแก้เวอร์ชันที่ยืนยันแล้วไม่ได้
117. ข้อห้ามที่เหลือป้องกันข้อมูลเสีย ไม่ใช่เรื่องสิทธิ์: ลบรายการที่มีเอกสารต้นทุนผูกอยู่ไม่ได้ (ให้แก้ปริมาณเป็น 0), เปลี่ยนรายการที่มีเอกสารต้นทุนเป็นงานลดไม่ได้, ลบรายการนอก BOQ ไม่ได้
118. ปุ่มแก้ไข BOQ ในหน้าโครงการของฝ่ายบริหารพาไปหน้าเวอร์ชันที่ยืนยันแล้วโดยตรง VO ยังมีไว้สำหรับงานเพิ่มลดที่ตกลงกับลูกค้าใหม่และต้องการเก็บเป็นเวอร์ชันแยก

## ช่องกรอกวันที่

119. ช่องวันที่ type="date" ของเบราว์เซอร์แสดงตามภาษาของเครื่อง เครื่องที่ตั้งภาษาอังกฤษจะเป็น เดือน/วัน/ปี ค.ศ. และเว็บบังคับรูปแบบไม่ได้ จึงเปลี่ยนเป็นช่อง DateInput ที่แสดง วัน/เดือน/ปี พ.ศ. เสมอ พิมพ์ตัวเลขได้เลย ระบบใส่ / ให้ รับปีได้ทั้ง พ.ศ. และ ค.ศ. และมีปุ่มปฏิทินเปิดตัวเลือกวันของเบราว์เซอร์ ค่าที่ส่งเข้าระบบยังเป็น YYYY-MM-DD เหมือนเดิม
120. หน้าแก้รายการ BOQ กรอกต้นทุนต่อหน่วยและราคาขายต่อหน่วยได้ทั้งแบบไม่รวมและรวม VAT (ช่องคู่แบบเดียวกับหน้าบันทึกการสั่งซื้อ) แทนการกรอก markup % เพราะผู้ใช้คิดเป็นราคาขาย markup คำนวณจากราคาขายเทียบต้นทุนและเก็บไว้ดู หน้าแก้แสดงกำไรต่อหน่วยและเตือนเมื่อราคาขายต่ำกว่าต้นทุน

## ซื้อเป็นหน่วยอื่นจาก BOQ

121. BOQ มักคิดเหล็กเป็นกิโล แต่ร้านขายเป็นเส้น ใบขอซื้อ ใบสั่งซื้อ และการรับของ เก็บปริมาณและราคาตามหน่วยที่ซื้อจริง พร้อม qty_factor (หน่วย BOQ ต่อหนึ่งหน่วยที่ซื้อ เช่น 1 เส้น = 299.4 kg) ยอดเงินจึงตรงทุกสตางค์ ไม่ต้องปัดราคาต่อกิโล ส่วนการเทียบกับ BOQ แปลงเป็นหน่วย BOQ ก่อนเสมอ ทั้งปริมาณที่สั่งแล้ว เกิน BOQ และราคาเทียบต้นทุน (migration 20261017_0012)
122. เลือกเหล็กที่ BOQ คิดเป็นกิโลและรายการบอกน้ำหนักต่อเมตรกับความยาว (เช่น 49.9 kg/m, Size 6 m.) ระบบตั้งให้ซื้อเป็นเส้นพร้อมตัวแปลงให้อัตโนมัติ แก้ได้ และปิดได้ถ้าซื้อเป็นกิโล
123. เอาช่องวันที่ต้องการออกจากหน้าบันทึกการสั่งซื้อตามที่ผู้ใช้ขอ คอลัมน์ในฐานข้อมูลยังอยู่และเป็นค่าว่าง

## อ่านรูปใบสั่งซื้อด้วย Claude

124. หน้าบันทึกการสั่งซื้อมีปุ่มถ่ายรูปหรือเลือกไฟล์ (JPG PNG WEBP PDF) Claude อ่านรายการ ผู้ขาย เลขที่ วันที่ ยอดรวม VAT และจับคู่แต่ละบรรทัดกับรายการ BOQ ของโครงการ ระบบกรอกบรรทัดลงฟอร์มให้ ผู้ใช้ตรวจแล้วกดบันทึกเหมือนเดิม การตรวจเกิน BOQ เกินต้นทุน และการบังคับเหตุผล ยังทำตามปกติ
125. ตัวเลขในเอกสารต้องให้ Claude อ่านจากรูป แต่ห้ามคำนวณหรือเติมเอง โค้ดตรวจ ปริมาณ × ราคา = ยอดบรรทัด, ผลรวมรายการ = ยอดรวม, VAT 7%, ยอดสุทธิ ถ้าไม่ตรงแสดงเป็นกรอบแดงว่าอาจอ่านผิด
126. ส่วนลดท้ายบิลเฉลี่ยลงราคาต่อหน่วยทุกบรรทัดตามสัดส่วน และถ้าราคาในเอกสารรวม VAT ระบบถอด VAT ให้ ต้นทุนในระบบจึงเป็นราคาที่จ่ายจริงก่อน VAT
127. หน่วยในเอกสารต่างจาก BOQ: ใช้ตัวแปลงเหล็กจากชื่อรายการ BOQ ก่อน (แม่นกว่า) ถ้าไม่มีใช้ตัวแปลงที่ Claude เสนอพร้อมบอกให้ตรวจ ถ้าไม่มีทั้งสองอย่าง ปล่อยให้ผู้ใช้กรอก ฟอร์มไม่ยอมบันทึกจนกว่าจะกรอก
128. ไฟล์ที่แนบเก็บใน project-files ใต้ projects/{id}/purchases/ และผูกกับรายการสั่งซื้อ (migration 20261017_0013) หน้ารายการสั่งซื้อมีลิงก์เปิดเอกสารแนบ ถ้า Claude อ่านไม่ได้ ไฟล์ยังแนบไว้และผู้ใช้กรอกเองได้
129. รูปถูกย่อในเบราว์เซอร์ไม่เกิน 2,000 พิกเซลเป็น JPG ก่อนส่ง เพราะ Vercel รับ request ไม่เกิน 4.5MB และแปลงรูป HEIC ของ iPhone ไปด้วย ขยาย bodySizeLimit ของ server action เป็น 4MB ซึ่งแก้ปัญหาไฟล์ BOQ ที่เกิน 1MB นำเข้าไม่ได้ไปด้วย
130. ไฟล์ V099 นำเข้าไม่ได้ด้วย numeric field overflow สาเหตุที่เป็นไปได้มากที่สุดคือ markup ที่คำนวณจากราคาขายหารต้นทุนเกินช่อง ±9,999.99% เมื่อต้นทุนต่ำมาก จำกัดค่า markup ไว้ในช่วงนี้ (เก็บไว้ดูเท่านั้น) ตรวจปริมาณและราคาที่ใหญ่ผิดปกติก่อนบันทึกพร้อมบอกชื่อรายการ และนำเข้าไม่สำเร็จจะลบเวอร์ชันร่างที่ค้างครึ่งๆ ทิ้ง

## คอลัมน์ต้นทุนต้องอ่านใหม่ทุกไฟล์

131. ไฟล์ BOQ แต่ละงานวางคอลัมน์ต้นทุนไม่ตรงกัน (V098 อยู่ U ถึง X งานหลังคาหลังที่ 2 อยู่ O ถึง S) template ที่จำตำแหน่งจากไฟล์ก่อนเคยชี้ไปคอลัมน์ว่าง ทุกรายการจึงใช้ราคาขายเป็นต้นทุน กำไรเป็นศูนย์ ผู้ใช้กำหนดว่าระบบต้องอ่านและคิดใหม่ทุกไฟล์ ห้ามยึดตำแหน่งตายตัว
132. เมื่อ Claude ทำงาน ใช้ผลของ Claude ที่อ่านไฟล์นี้ก่อน template ไม่ถูกใช้เลย template ใช้เฉพาะตอน Claude ไม่ทำงาน และไม่เก็บตำแหน่งคอลัมน์ต้นทุนข้ามไฟล์
133. โค้ดตรวจคอลัมน์ต้นทุนที่ Claude เลือกว่ามีตัวเลขในบรรทัดรายการจริง ถ้าว่าง ลองคอลัมน์ที่หัวคอลัมน์ในไฟล์นี้เขียนว่าเป็นต้นทุน แล้วใช้ชุดที่มีต้นทุนครบกว่า ถ้าทุกรายการยังไม่มีต้นทุน หน้านำเข้าแสดงกรอบแดงให้เลือกคอลัมน์เอง
134. ตัวตรวจตัวเลข: "ราคารวมค่าดำเนินการ" เป็นยอดรวม ไม่ใช่ค่าดำเนินการอีกบรรทัด และแถว รวม ที่ผู้ประมาณราคาทดไว้ข้างตารางก่อนรายการแรกไม่ถูกตรวจเป็นยอดต้นทุนหมวด
135. หน้าบันทึกการสั่งซื้อรับรูปจาก Ctrl+V ได้ทั้งหน้า (copy รูปหรือ capture หน้าจอแล้ววาง) ถ้ากำลังพิมพ์ในช่องกรอกและ clipboard มีข้อความด้วย ให้วางข้อความตามปกติ ไม่แย่งไปอ่านเป็นรูป
136. ซื้อเป็นหน่วยอื่นจาก BOQ เว้นช่องตัวแปลงหน่วยว่างได้ (ผู้ใช้ขอ เช่น ซื้อเป็นชุดแต่ BOQ คิดเป็น m2 และยังไม่รู้ว่า 1 ชุดเท่ากับกี่ m2) ยอดเงินนับเข้าต้นทุนของรายการ BOQ ครบ ผู้ใช้ไปดูทุนเทียบราคาขายเองในหน้าสรุปต้นทุน บรรทัดนั้นไม่เทียบปริมาณเกิน BOQ และราคาต่อหน่วยกับต้นทุน (ไม่ตั้งธง ไม่บังคับเหตุผล) และไม่นับปริมาณเข้าปริมาณที่สั่งหรือรับ เพราะไม่รู้ว่าเท่ากับกี่หน่วย BOQ (migration 20261017_0014)
137. เติมหรือแก้ตัวแปลงหน่วยของรายการสั่งซื้อที่บันทึกไปแล้วได้จากหน้ารายการสั่งซื้อ (สิทธิ์เดียวกับ can_manage_project) ฟังก์ชัน set_purchase_qty_factor แก้ทั้งบรรทัดใบขอซื้อและบรรทัดใบสั่งซื้อที่ออกจากบรรทัดนั้น ปริมาณที่สั่งและรับในหน่วย BOQ เปลี่ยนตามทันที ยอดเงินไม่เปลี่ยน คำนวณธงเกิน BOQ และเกินราคาที่ทดไว้ใหม่ไว้แสดง แต่ไม่บังคับเหตุผลย้อนหลัง ล้างกลับเป็นไม่ทราบได้ หน้ารายการสั่งซื้อมีตัวกรอง ยังไม่ระบุตัวแปลงหน่วย (migration 20261017_0015)
138. อ่านรูปใบสั่งซื้อได้โดยไม่ต้องเลือกโครงการก่อน Claude อ่านเลข JOB ที่พิมพ์ในเอกสาร (เช่น A6910-05(V100)) โค้ดเทียบรหัสงานทั้งก้อนกับรหัสและชื่อโครงการ ถ้ารหัสงานซ้ำใช้เลขเวอร์ชัน V แยก ถ้าโค้ดหาไม่เจอจึงใช้โครงการที่ Claude เลือกจากชื่องานพร้อมบอกให้ตรวจ ถ้าหาไม่ได้เลยให้ผู้ใช้เลือกโครงการแล้วอ่านใหม่
139. เมื่อยังไม่รู้โครงการ การอ่านรูปครั้งแรกไม่จับคู่ BOQ เมื่อหาโครงการได้แล้วจึงจับคู่บรรทัดกับ BOQ ด้วยการเรียก Claude แบบข้อความล้วน ไม่ส่งรูปซ้ำ ไฟล์แนบอัปโหลดหลังรู้โครงการ ถ้าผู้ใช้เลือกโครงการไว้แล้วแต่เลขงานในเอกสารตรงกับโครงการอื่น ระบบเตือนแต่ไม่เปลี่ยนให้
140. แนบเอกสารจัดซื้อได้หลายใบในครั้งเดียว คละงานได้ แต่ละใบอ่านแยกกัน หาโครงการจากเลข JOB ของตัวเอง และกลายเป็นหนึ่งรายการสั่งซื้อพร้อมฟอร์มของตัวเอง ผู้ใช้ตรวจและกดบันทึกทีละใบ บันทึกแล้วไม่เปลี่ยนหน้า ทำใบถัดไปต่อได้ ไม่ได้แนบเอกสารใช้ฟอร์มกรอกเองตามเดิม
141. การอ่านเอกสารย้ายจาก Server Action ไปเป็น Route Handler (/api/purchase-documents) เพราะ Next.js ส่ง Server Action ทีละคำขอ หลายใบจะอ่านได้ทีละใบ และปุ่มบันทึกต้องรอการอ่านที่ค้างทั้งหมด อ่านพร้อมกันได้สูงสุด 3 ใบ ที่เหลือรอคิว
142. ใบที่หาโครงการจากเลขงานไม่ได้ ระบบเก็บผลอ่านไว้และให้ผู้ใช้เลือกโครงการ แล้วจับคู่ BOQ ด้วยข้อความล้วนโดยไม่ให้ Claude อ่านรูปซ้ำ ผลอ่านที่ส่งกลับมาจากเบราว์เซอร์ตรวจรูปแบบด้วย schema เดิมก่อนใช้ และไฟล์แนบอัปโหลดตอนรู้โครงการแล้ว

## รายรับ: วางบิลและเงินเข้าจริง

143. วางบิลลูกค้าเป็นงานของฝ่ายบัญชี ฝ่ายบริหารและผู้ดูแลระบบบันทึกและแก้ไขแทนได้ ผู้ที่เห็นโครงการเห็นยอด แต่ละบิลเก็บยอดไม่รวม VAT และ VAT แยก เลขที่ใช้ตามเอกสารจริงหรือให้ระบบออกเลข BL ยกเลิกบิลได้พร้อมเหตุผล แต่บิลที่รับเงินแล้วต้องลบรายการรับเงินก่อน
144. รับเงินบันทึกเงินเข้าบัญชีจริงแยกจากยอดที่ลูกค้าหัก (ภาษีหัก ณ ที่จ่าย เงินประกันผลงาน หักอื่น) บิลปิดเมื่อ เงินเข้า + ยอดที่ถูกหัก ครบยอดรวม VAT รับครั้งแรกเต็มบิล ระบบเสนอหัก ณ ที่จ่าย 3% และเงินประกันตาม % ในสัญญาของโครงการ แก้ได้ทุกช่อง
145. เงินเข้าที่ไม่ผูกบิลบันทึกได้ เช่น ลูกค้าคืนเงินประกันผลงาน ซึ่งลดยอดเงินประกันที่ลูกค้ายังถือไว้ หน้าโครงการแสดงวางบิลแล้วกี่ % ของมูลค่าสัญญา เงินเข้าจริงเทียบต้นทุนจริง ค้างรับ และเงินประกันที่ลูกค้าถือไว้ (migration 20261029_0016)

## ผู้ใช้และสิทธิ์

146. ฝ่ายบริหารและผู้ดูแลระบบเพิ่มผู้ใช้ได้จากหน้าผู้ใช้และสิทธิ์ ระบบสร้างบัญชีพร้อมรหัสผ่านชั่วคราวแสดงครั้งเดียว ไม่ส่งอีเมล เพราะอีเมลของ Supabase ค่าเริ่มต้นส่งได้จำกัด ผู้ใช้เปลี่ยนรหัสผ่านเองที่เมนูเปลี่ยนรหัสผ่าน เปลี่ยนสิทธิ์ ปิดเปิดบัญชี และตั้งรหัสผ่านใหม่ได้ เปลี่ยนสิทธิ์หรือปิดบัญชีตัวเองไม่ได้ เฉพาะผู้ดูแลระบบให้หรือแก้สิทธิ์ผู้ดูแลระบบได้ ต้องตั้ง SUPABASE_SERVICE_ROLE_KEY บนเซิร์ฟเวอร์
147. ผู้ใช้ที่ใช้งานและแก้ไขได้ทุกฟีเจอร์ให้สิทธิ์ฝ่ายบริหาร
148. มีหน้าสมัครใช้งาน (/register) ผู้สมัครกรอกชื่อ อีเมล รหัสผ่าน และตำแหน่ง ระบบสร้างบัญชีด้วย service role แบบยืนยันอีเมลแล้ว ไม่ต้องพึ่งอีเมลของ Supabase บัญชีเริ่มเป็นวิศวกรและยังไม่เปิดใช้งาน ฝ่ายบริหารและผู้ดูแลระบบได้รับแจ้งเตือน แล้วเลือกสิทธิ์และกดเปิดบัญชีที่หน้าผู้ใช้และสิทธิ์ ผู้สมัครที่รออยู่ขึ้นบนสุด
149. ปิดช่องโหว่สองจุด ฐานข้อมูลเคยอ่านสิทธิ์ของบัญชีใหม่จาก user_metadata ซึ่งผู้สมัครกำหนดเองได้ตอนเรียก signUp ผ่าน API ของ Supabase จึงสมัครเป็นฝ่ายบริหารได้ ตอนนี้อ่านจาก app_metadata ซึ่งตั้งได้ด้วย service role เท่านั้น และตัวกันแก้สิทธิ์ตัวเองเดิมไม่ทำงานกับบัญชีที่ยังไม่เปิดใช้งาน (สิทธิ์เป็น null) บัญชีที่รออนุมัติจึงเปิดบัญชีตัวเองได้ แก้ให้แก้สิทธิ์ สถานะบัญชี และสาขาได้เฉพาะฝ่ายบริหาร ผู้ดูแลระบบ หรือ service role (migration 20261029_0017)
